# 多人协作与 AI 任务边界

## 核心规则

使用 AI 不会自动造成重复；重复通常来自任务描述没有限定“负责人、允许修改的文件、接口和验收条件”。每项任务必须同时写清这四件事：

1. 负责人和分支；
2. 允许修改的目录/文件；
3. 输入输出接口；
4. 可执行的完成判据。

任何任务都不能用“把整个项目做好”作为目标。

## 三人协作

| 负责人 | 固定边界 | 主要文件 |
|---|---|---|
| 第一轮任务 T-001/T-002/T-003 | 分别负责一个音频 RTL 小闭环；每项都必须有 testbench 和结果 | 见 `docs/task-board.md` |
| 集成轮换 | 三人轮换做顶层、音频核心和验证，避免固定的“主开发/辅助”角色 | 由每轮任务卡指定 |

资料查找、文档和测试不是某个人的固定岗位；谁负责一个模块，谁就负责该模块所需的资料、测试和交接说明。

## 冻结的交接接口（v0）

交互模块不直接操作振荡器寄存器，只产生演奏事件：

```text
note_event:
  valid       : 1 bit, one-cycle pulse
  note_id     : 7 bit
  note_on     : 1 bit
  velocity    : 8 bit
  expression1 : 8 bit
  expression2 : 8 bit
  expression3 : 8 bit
  instrument  : 2 bit
```

音频核心不直接驱动引脚，只产生采样数据：

```text
audio_sample:
  sample_ce : 1 bit
  pcm_l/r   : signed 24 bit (内部可保留保护位)
```

`note_event` 可以先由 testbench 产生，之后再替换成按键、压力或电位器适配器；`audio_sample` 可以先接固定测试音，再接合成核心。只要接口不变，输入方案和合成算法可以独立更换。

## 分支与合并

- 每项任务使用 `feat/<task-id>`；不得在同一工作区同时改同一文件。
- `main` 只接受可综合、带测试结果的提交。
- 集成工作按任务卡轮换；同一时刻只允许一人编辑 `src/top.v` 或工程文件，其他人通过接口提交模块。
- 每个提交只解决一个小问题，例如 `feat: add i2s transmitter` 或 `test: add adsr assertions`。
- 合并前必须说明：改了哪些文件、接口是否改变、运行了什么仿真/综合、结果是什么。

如果多人在同一台电脑上工作，最好分别使用 Git worktree；至少也要先提交、切换分支后再交给另一人。不要让两个 AI 会话同时在共享目录里编辑文件。

所有人使用 AI 都可以，但每次对话都要把任务卡放在第一条消息里，并明确“只改这些文件”。不要使用“继续完善项目”“把音频做好”这类没有边界的请求。AI 完成后先停在分支提交，另一人再审查和合并；不要让 AI 直接把两个未完成模块拼到 `main`。

## 给 AI 的任务模板

```text
任务：实现 <一个明确模块>
负责人/分支：<姓名> / <branch>
允许修改：<明确文件列表>
禁止修改：<其他目录，尤其是顶层和另一人的模块>
接口：严格遵守 docs/team-workflow.md 的 v0 接口
完成条件：<仿真、断言、综合或文件检查>
如果发现接口不够：先报告，不要擅自改接口或扩大文件范围
完成后报告：变更文件、测试命令、结果、已知风险
```

## 第一阶段任务切片

1. T-001：相位累加器；T-002：ADSR；T-003：混音限幅，三项互不修改对方文件。
2. 三项完成后，由当轮指定的集成人建立单声部仿真顶层。
3. 板卡到货后再建立固定测试音和 I2S TX 工程顶层。
4. 固定音通过后，接入音频核心并扩展到 4 声部。
5. 基础链路稳定后，轮换任务负责人继续做交互、32 声部和效果器。

每项完成后先合并，再开始下一项依赖任务。这样既能并行开发，也能让每次合并都保留一个可回退的工作状态。
